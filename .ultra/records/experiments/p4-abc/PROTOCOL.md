## 要回答的问题

## 三组

所有组的写者相同：Claude `implementer` 子代理，新上下文，只拿到 `ubp context` 编出的节点简报和一段固定的任务说明（`missions/` 下逐字保存）。

- **A 单写者**：写者 → 控制者验收（作用范围、`ubp check` 全量、`node done`）。
- **B = A + 并行只读探索和测试**：
  - 写者开工前，一个只读 `Explore` 代理按简报画出相关代码地图，不超过 300 字，附在写者的任务说明末尾；
  - 写者完成后，一个只读测试代理对照需求跑全部检查，并手动探测 API，返回发现；
  - 有发现时，写者返工一轮。
- **C = B + 跨厂商评审**：写者完成后，Codex 只读评审写者的 diff，和测试代理并行；两方的发现合并后，写者返工一轮。

## 单元

R 在 M2 关闭后的提交上，取三个新任务。每个任务在三组里各跑一次，共 9 个单元，配对设计。每个单元在 R 的独立克隆里运行，互不干扰。

- **T1 自定短码**：`POST /api/links` 接受可选的 `code`（4–10 位 ASCII 字母或数字）。格式不对回 400，已被占用回 409。
- **T2 单条查询**：`GET /api/links/<code>` 返回列表里同样的对象；未知短码回 404。
- **T3 重复链接**：对已存在且永不过期的同一链接再次创建，回 200 并返回原有链接，不新建。

每个任务有两套检查，都由我（验收作者）在开跑前写好：

- **可见检查**：给写者看，开跑前在克隆里必须是红的。
- **隐藏检查**：写者看不到，单元结束后才运行，用来度量漏掉的缺陷。

## 每个单元记录什么

| 指标 | 怎么量 |
|---|---|
| 墙钟时间 | 控制者记录从派出写者到 `node done` 成功的时间，含探索、测试、评审和返工 |
| 写者 token / 其余代理 token | 各代理回执里的 usage；Codex 记它回执里的数字，没有就记“未知” |
| 返工轮数 | 0 或 1 |
| 可见检查首轮通过 | 写者第一次 `node done` 是否成功 |
| 隐藏检查通过率 | 通过条数 / 总条数 |
| 控制者介入 | 次数和原因 |
| 合并冲突 | 各单元在独立克隆里跑，记 0；本实验不检验并行写者 |
| 上下文重建 | 写者报告里提到的“重新读了哪些文件”，只作定性记录 |

## 停止规则（事先写定）

1. 每个单元最多返工一轮。超过 45 分钟墙钟仍未 `node done` 的单元，记为失败，停止该单元。
2. 某组连续两个单元因同一个机制故障（不是写者能力问题）失败时，停止该组，并记录原因。
3. 9 个单元全部跑完或停止后才看汇总，中途不改方案。

## 判定规则（事先写定）

- **B 或 C 升为默认**的条件：与 A 配对比较时，3 个任务里至少 2 个的隐藏检查通过率更高，没有一个任务更低，并且总 token 不超过 A 的 2 倍。
- 达不到上述条件时，**默认仍是 A**；B 或 C 只作为可选做法，写明适用于哪类任务。
- 每组只有 3 对，统计上只能看出很大的差异，所以结论只写“方向性证据”，不写“证实”。

## 可推翻条件

在 Owner 的第一个真实样本上，如果出现 A 漏掉、而 B/C 的那类检查本可抓到的缺陷，并且同类缺陷出现两次，就重开这个决定。

方案：`PROTOCOL.md`（开跑前写定，开跑后只追加偏离记录）。原始数据：`data/`。9 个单元全部结束后，才第一次读隐藏检查日志（2026-11-01）。

## 结论

**默认分工保持 A：单写者 + 控制者核验。** B 和 C 都没有满足预先写定的升级条件，结论属于“方向性证据”。

- 隐藏检查：三组在每个任务上的通过数完全相同，B、C 没有一个任务比 A 高。
- 花费：B 的 token 是 A 的 3.3–3.8 倍，C 是 3.6–5.2 倍（C 还不含 Codex 的 token，回执里没有），都超过了“不超过 2 倍”的上限。
- 墙钟时间：B 是 A 的 2.7–3.5 倍，C 是 2.7–4.5 倍。

## B、C 多出来的角色实际做了什么

- **测试代理**（B、C 共 6 次）：都回报“No findings”，探测了几十到上百个请求，没有找出可见检查之外的缺陷。
- **Codex 评审**（C，3 次）：T1、T2 没有发现；T3 找到 1 个真实缺陷——网页表单先 `trim()` 再去重，用 API 存了带尾部不换行空格的链接后，从网页提交同样的链接会重复创建。写者返工一轮修好（`a6bb024`）。隐藏检查没有覆盖这个情况，所以它没有反映在通过率里。Codex 的沙箱不能监听端口，三次都只能读代码评审。
- **探索代理的地图**（B、C 共 6 份）：
  - T3-C 的地图指出任务规格本身有冲突：R 的 REQ-create 写着“两次创建得到两个不同的短码”，与 REQ-dedupe 矛盾。这是验收作者留下的 L1 冲突，A 和 B 的写者都没有提。
  - T3-B 的地图让写者“别把未提交的 evidence.jsonl 带进提交”，结果写者把自己的账本行也留在了工作区，由控制者补提交。
  - 3 份地图超长或换了语言（T1-C 302 词、T3-C 309 词、T2-B 用中文写成）。
- **可见检查首轮未过**只有 T2-B 一次：写者写的裁决行格式不对，`node done` 被计划门拦下，写者自己改好。

## 解读和局限

- 每组只有 3 对，任务也偏小（一个节点，改一两个文件），只能看出很大的差异。三个任务里 A 的写者都一次做对，留给 B、C 发挥的空间很小。
- 隐藏检查由验收作者写，覆盖面有限；C 组抓到的那个缺陷就不在其中。在更复杂、跨多个模块的节点上，跨厂商评审的价值可能更高，这次没有测到。
- 写者都是同一个模型（Claude Sonnet 档的 `implementer` 子代理）；Codex 只做评审，没有当写者。

## 由此写进方法的默认分工

见 `.ultra/decisions/2026-11-01-p4-default-roles.md`：
- 每个节点只派一个写者，之后由控制者核验，不加探索、测试或第二位评审；
- 跨厂商评审留给里程碑门的整分支评审；
- 规格冲突靠规划者在计划门之前读一遍需求之间的关系，不靠每个节点的探索。

可推翻条件（预先写定）：在 Owner 的第一个真实样本上，如果 A 漏掉了 B、C 那类检查本可以抓到的缺陷，并且同类缺陷出现两次，就重开这个决定。

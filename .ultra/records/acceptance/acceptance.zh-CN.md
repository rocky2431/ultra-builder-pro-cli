## 1. 成品：UBP v6.0.0 是什么样

### 装上之后宿主里有什么

| 部件 | 内容 |
|---|---|
| 一个 Skill `ultra` | 方法全文（`skills/ultra/SKILL.md`）。Claude Code 里输入 `/ultra`，Codex 里输入 `$ultra-builder-pro:ultra` |
| 一份引擎 `ubp` | `engine/` 下 17 个 `.cjs` 文件，只用 Node 内置模块，共 1983 行。受保护的预算测试按每个文件多算一行，合计正好 2000 行，是合同上限 |
| 一个 SessionStart hook | 只在含 `.ultra/spec.md` 的项目里打印进度行，再加一句 `Use the ultra Skill to drive this project.`；其他地方什么都不做 |
| 宿主 | 只有 Claude Code 和 Codex。npm 包共 37 个文件，含 drive 的两个示例脚本 |

移出默认路径的有：5.x 的十四个 Skill、五个 Python hook、OpenCode/Kimi/Grok/ZCode 适配器，以及 `run`、`delegate`、ACP/Pi 执行、durable grant、wake-up。它们在 Git 历史里都能找回；npm 上最后发布的 5.x 是 5.0.1（之前说明里写的“已发布的 5.0.2”有误，已更正）。

### 用起来是什么样

项目真相全部放在 `.ultra/` 下：

- `spec.md`：需求，每条都有编号；
- `checks.json`：可执行的检查，每条写明覆盖哪些需求；
- `plan.json`：里程碑和节点；
- `ledger/*.jsonl`：证据、节点完成、计划日志、批准、里程碑关闭；
- `rulings.md`：裁决；
- `records/`：评审、交接、Owner 介入记录。

进度由引擎从这些文件和检查证据算出来，不靠任何人汇报。每个会话开头会看到这样的进度行（hook 后面还会加一句 `Use the ultra Skill to drive this project.`）：

```
M3 · 0/3 绿 · 3 红 · 下一项 N-custom-code · 本里程碑计划变更 1 次
```

- 需求只有五种状态：绿、红、未知、过期、未覆盖。“未知”永远不算绿。
- 改了需求原文，只有和它关联的检查和节点变成过期（差分失效）。
- 删需求、删检查、缩小覆盖范围都会被引擎拦住，要你批准（`ubp approve`）才能做。
- 已经绿的需求又变红叫“棘轮破坏”。合并门、drive 和里程碑关闭会拦；手动的 `ubp node done` 只查本节点的需求和不变量（清理节点另查已关闭的里程碑），别处变红要靠控制者在 `check` 之后发现。

| 命令 | 作用 |
|---|---|
| `ubp status` | 算出进度和下一步 |
| `ubp gate` | 计划门：校验计划，记下基线和变更 diff |
| `ubp check [ids]` | 运行检查并记证据 |
| `ubp node done <id>` | 需求全绿时记节点完成 |
| `ubp context <id>` | 编译节点简报（写者只看这个） |
| `ubp milestone close <id> --owner "原话" --review <file>` | 关闭已评审的里程碑 |
| `ubp approve <items> --owner "原话"` | 记录对缩小范围的批准 |
| `ubp retro` | 列出重复出现的失败类别 |
| `ubp merge <branch> --expect-head <sha>` | 合并门：校验并合并并行写者的分支 |
| `ubp drive --writer <cmd> [--reviewer <cmd>]` | 无人值守地推进节点，直到下一个需要你的点 |

需要你本人出面的有四处：0→1 访谈（为谁做、成功条件、边界）、里程碑门（看演示和评审，答“放行还是改方向”）、缩小范围、方向（L0）的变化。其余由模型自己推进。

### 无人值守：`ubp drive`

drive 一个节点接一个节点地跑：编译简报，交给写者，然后逐项核验。核验项有：

- 真相文件没被改；
- 历史没被改写；
- 工作区干净，包括 Git 的隐藏标记（`assume-unchanged`、`skip-worktree`）和仓库自己的 Git 设置（`config`、`config.worktree`、`info/exclude`）；
- 改动都在节点的 scope 内，没碰检查文件；
- 计划门通过；
- 棘轮没破；
- 节点的检查和全部不变量都是绿的。

到了里程碑门，它让评审跑一次，然后停下。它从不关闭里程碑，也从不批准任何事。无头 `claude -p` 的写者和评审示例随包发布在 `docs/examples/drive/`（安装器不把它们复制进宿主）。

## 2. 样本 R：Shortlink

- **位置**：`../ubp-sample-shortlink`，本地独立仓库，没有远端。
- **它是什么**：一个人或一个小团队在自己机器上跑的短链接服务。粘贴长链接，得到短链接；打开短链接，跳回原来的地址；能看到每条链接被打开了几次。
- **“优雅”在这里的意思**：零 npm 依赖，`npm start` 一条命令启动，数据存在一个本地 JSON 文件里，代码短到一次读完（`src/` 共 454 行）。
- **规模**：11 条需求、12 条检查、3 个里程碑。

| 里程碑 | 内容 | 怎么做的 | 门评审 | 状态 |
|---|---|---|---|---|
| M1 | 缩短、跳转、计数、持久化、网页 | 宿主内单写者，从访谈开始 0→1（P2） | 2 轮。第 1 轮发现约 54 MB 的长链接会让首页崩溃，于是加了 64 KiB 上限（缩小范围，代答批准） | 已关闭（代答） |
| M2 | 会过期的链接、API 删除 | 进行中注入四种变更：L1 新增、修改、缩小，L2 设计变更（P3） | 2 轮 | 已关闭（代答） |
| M3 | 自选短码、按短码查一条、同一个链接只缩短一次 | `ubp drive` 无人值守写节点（P5a），drive 共启动 4 次（第 0 次写者没起来） | 2 轮 revise（都是代码对、检查弱），共补 7 条断言和 6 个测试，不改代码；之后一次窄核对 accept | 已关闭（代答） |

### 实验

- **A/B/C（P4）**：比较三种分工：A 单写者；B 加探索和测试角色；C 再加跨厂商评审。三组在隐藏检查上得分相同；B 的 token 是 A 的 3.3–3.8 倍，C 是 3.6–5.2 倍。默认分工因此定为 A。可推翻条件已事先写定：在你的真实样本上，A 漏掉同类缺陷两次。
- **方法进化门槛（P5b）**：候选是“写者手工探测检查没覆盖的地方”。12 次开发集运行，两组的隐藏检查都是满分，增益为 0，所以拒绝（未证实）。采纳与否由你决定，按预注册规则建议不采纳。

1. **每句需求先列出它的输入类别，以及新路径经过的每条旧路由，再写检查**（规划时一次，节点完成时再对一次）。这是这次最重要的发现：

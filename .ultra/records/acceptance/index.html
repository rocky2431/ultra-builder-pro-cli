用起来是什么样

项目真相全在 .ultra/ 下：spec.md（编号的需求）、checks.json（可执行的检查和它覆盖的需求）、plan.json（里程碑和节点）、ledger/*.jsonl（证据、完成、计划日志、批准、关闭）、rulings.md（裁决）、records/（评审、交接、Owner 介入）。进度由引擎从这些文件和检查证据算出来，不靠任何人汇报。每条需求只有五种状态：

  • 绿 检查在当前代码上通过
  • 红 检查失败
  • 未知 没跑过，永远不算绿
  • 过期 需求或代码变了
  • 未覆盖 没有检查
  • 改了需求原文，只有和它关联的检查和节点变成过期（差分失效）。
  • 删需求、删检查、缩小覆盖范围都会被引擎拦住，要你批准（ubp approve）。
  • 已经绿的需求又变红叫“棘轮破坏”。合并门、drive 和里程碑关闭会拦；手动的 node done 只查本节点的需求和不变量，别处变红要靠控制者在 check 之后发现。
  • 需要你本人出面的有四处：0→1 访谈（为谁做、成功条件、边界）、里程碑门（看演示和评审，答“放行还是改方向”）、缩小范围、方向（L0）的变化。

无人值守：ubp drive

drive 一个节点接一个节点地跑：编译简报，交给写者，然后自己逐项核验，不信写者交来的证据：

  1. 真相文件没被改；
  2. 历史没被改写；
  3. 工作区干净，包括 Git 的隐藏标记（assume-unchanged、skip-worktree）和仓库自己的 Git 设置（config、config.worktree、info/exclude）；
  4. 改动都在节点的 scope 内，没碰检查文件；
  5. 计划门通过；
  6. 棘轮没破（当前和已关闭的里程碑）；
  7. 节点的检查和全部不变量都是绿的。

到了里程碑门，它让评审跑一次，然后停下。它从不关闭里程碑，也从不批准任何事。每个节点最多试 3 次，整次运行最多启动 10 个写者。

无头 claude -p 的写者和评审示例随包发布在 docs/examples/drive/（安装器不复制进宿主）。它们调用引擎写成 eval "$UBP <参数>"：代理的登录 shell 里普通的 ubp 可能是别的程序，这台机器上就是（第 0 节）。

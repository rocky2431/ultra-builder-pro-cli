## 助手先验判断（2026-10-31，调研前写下，未经 Owner 接受）

- H11（自进化，调研前）：
  - 把要进化的东西分成两类：
    - 项目知识：每个 Change 都可以改，靠 Git 追溯；
    - 方法本身（skill、剧本）：变得慢，只能以候选版本的形式出现。
  - 候选方法必须在固定的、留出的任务集上与当前版本对比，提升超过事先定好的最小值才晋升。被拒的候选和理由要留档。
  - 晋升由 Owner 决定。
  - 多套方案并存时，按任务类型路由到当前的最优版本，不混用。
  - 风险：样本太少、噪声大，容易把单个项目的经验误当成通用规律。

- H1 真相单位：带编号的行为规格加上可运行的验收，而不是 task。计划和任务图是由规格推导出来的，可以丢弃、重新生成。
- H2 "改 spec 还是改别的"：先判断发现的问题属于哪一层，再改那一层。
  - 方向（为什么做）改北极星；
  - 行为（做什么）改规格条目，用增、改、删的差分；
  - 方案（怎么做）改设计决策；
  - 执行细节不往上改。
  改哪一层，就让依赖这一层的节点失效。
- H3 1→100 的熵分两种，各自对应解法：
  - 真相漂移：靠可运行的验收，并且所有历史条目永久参与回归（棘轮）；
  - 结构侵蚀：靠机械执行的架构不变量，加上里程碑处的清理节点；同时每次修改前先读这一片区域的历史。
- H4 graph 加 loop：任务图由"规格差分 × 代码现状"编译而来，像构建系统一样增量失效。loop 只放在节点内部，并设上限。方向判断放在里程碑边界，或在节点上报"这是规格问题"时进行。进度 = 当前规格版本下通过的条数 / 总条数。并行由图上的独立性推出。
- H5 上下文切割：每个节点的上下文按它在图中的位置编译，包括覆盖的规格条目、适用路径上的不变量、邻接接口、相关决策和这一片区域的教训。hook 只给指针。
- H6 多 Agent：
  - 判断由机器做（验收）；
  - 评审由另一个厂商的模型做（独立性）；
  - 只有图上同时出现两个以上独立且有分量的节点时才并行，因为我们自己的 Factory 数据显示并行没有稳定收益。
- H7 Owner 只在三处介入：开始时的意图与规格、里程碑门禁、节点上报的方向或行为问题。
- H8 辨识度候选：意图是源码，计划是编译产物，进度靠计算，变化是一条差分。
- H9 风险：
  - 再次去造工厂机制，而不是先打磨方法；
  - 0→1 过度规格化。缓解办法是规格只写到行为层，把探索型的"回答"节点作为一等公民。
- H10 落地：先在一个真实外部项目上做一条最薄的纵向切片（规格格式、验收执行器、任务图编译、进度视图、单节点 loop），多 Agent 和跨厂商以后再加。

**04 多 Agent 编排**（`research/04-multi-agent-orchestration.md`，1/6）

- **H6 降级。** 原先认为"评审由另一个厂商的模型做，可以带来独立性"。报告里只有一项受控实验（arXiv 2607.21656，[摘要]），而且同一对模型在两个方向上的结果相反。Cognition 的报告是：同一个模型，只要换成干净的上下文来评审，就有效（[直读]）。
  - 修正：评审的独立性先靠**干净上下文、不看作者的推理过程**来保证。跨厂商评审作为一个待检验的假设，用 A/B/C 三组对照来测：
    - A：单写者；
    - B：单写者，加上并行的只读探索和测试；
    - C：在 B 的基础上加跨厂商评审。
- **H4 补充。** Cursor 的实际经验（[直读]）：只有依赖图加人工派发时，吞吐量上去了，结果却没有变好。真正留下来的做法是：规划者不写代码；每个 worker 只做一项任务，做完写交接；删掉了 judge 和 integrator 这两个单点。
  - 修正：任务图之外，还需要**交接协议**和**合并门**。合并门要校验 expected head，红了就二分定位。另外，允许存在稳定的小错误率，定期做一轮修复，收敛成一个全绿的分支。
- **H6 补充。** 并行只放在只读、审查、测试类的节点上，写代码保持单写者。只有任务可以分解、结果能由机器判定、单个代理的基线又不高时，并行才划算。成本方面，Anthropic 报告多 Agent 的 token 用量约为普通聊天的 15 倍（[直读]）。
- **新约束（有文档依据，未实测）。** 在非交互模式（`-p` 或 Agent SDK）下，Claude Code 的 agent teams 不会派生 teammate。所以无人值守的工厂应该用 workflow 脚本或 SDK 会话。
- **解释我们自己的 Factory 数据。** 慢可能来自四个方面：协调等待、重建上下文、评审返工、合并冲突。之前没有按单元分别记录这四项，所以定位不了原因。

**02 规格驱动与变更**（`research/02-spec-driven-and-change.md`，4/6）

- **没有一家实现了可验证的 spec、代码、测试自动同步，也没有一家做到改动后的自动失效级联。**
  - Kiro 说 "stay synced"，但描述出来的机制是靠请求或手动更新。
  - OpenSpec 用 delta（ADDED/MODIFIED/REMOVED）记录改动，归档时合并，没有审批门。
  - BMAD 的做法：先改需求但保留 ID，把相关条目标记为过期，重新切分，再记一行 Decision；已经建成的部分不重写。
  - 结论：H4 设想的"改一条规格，只让依赖它的节点失效"，在这批项目里没有人做。它可以作为辨识度候选。但"没搜到"不等于"没人做过"；而且它必须做得便宜，靠稳定 ID 链（需求 → 任务 → 测试）来实现，不能靠语义猜测。
- **分母都来自清单，但"勾了"不等于"完成"，派生出来的计数也会悄悄算错。**
  - GSD 1.42.1：派生计数静默回退。
  - OpenSpec 1.14.2：基线无法恢复时，REMOVED 原本被当作通过，后改成"未验证"。
  - 结论：支持 H1，并补充两条——计数要从权威状态派生，计数器本身要有测试；"找不到"按"未验证"处理。
- **Superpowers 的几个做法：**
  - spec 是 "binding authority"；
  - 代理可以自己裁决，但要记成 `Ruling: … — what it costs if wrong`，只在四类情况下停下来问人；
  - 每份 plan 都复制一遍全局约束；
  - 收尾时对整条分支做一次评审。
  - 结论：这正好补全 H2 里"哪些决定可以由代理自己做"。需要事先写明哪些类别必须交给 Owner；其余的代理自己裁决，但必须记下"如果判断错了，代价是什么"。
- **演进的主要方向是做减法，而且大多附了原因：**
  - Superpowers 把每个 task 的两个评审合并成一个，原因是 "expensive and easy to game"；
  - OpenSpec 1.0 去掉了刚性的 propose → apply → archive 流程，改成按动作组织的图；
  - BMAD 删掉了文档分片；
  - GSD 删掉了代码智能子系统和 13 份重复的 prompt 副本。
  - 结论：支持"每个部件要能单独拆掉"。
- **繁琐程度要随改动大小缩放。**
  - Böckeler 的评价：Kiro 改一个小 bug 也 "way too verbose"，"I'd rather review code than all these markdown files"（只看了摘要）。
  - Superpowers 有过一次会话"从没问过平台，就做成了 web app"，说明意图澄清不能省。
  - 结论：0→1 可以重，1→100 的小改动必须轻。仪式随规模缩放，这一点必须写进设计。

## 当前判断（10-30，助手提出，未经 Owner 接受）

进度看不见、工程结束不了，有三层原因：

1. **没有分母**：大循环只有方向，没有清单。ultragoal 和原生 goal 也一样，只有一个终止条件，没有"总共几项、已完成几项"。
2. **完成由模型判定**：9 月 5 日诊断出的缺口一直没补。由模型判断是否收敛，它总能找到下一件可以做的事。
3. **清单里有不会结束的条目**：步骤 6、7 实际上是研究问题和可靠性上限，靠继续造东西是关不掉的。对研究型条目来说，得出否定结果就是完成。步骤 6 已经有了答案，即"收益不能重复"，但被当成"还没做完"，一直在循环。

更深一层：最近三个月 Ultra 主要在造它自己，没有一个外部项目在用它交付。没有外部用户，就没有人能说"够了"。

方向是保留"计划 → 任务 → 验证 → 交付"这个骨架，同时做四处修改：
- 用一份有限清单作分母。每条验收都带一条可以运行的检查，进度 = 通过的条数 / 总条数。改计划要显式进行，分母的变化必须看得见。
- 条目分两类：造东西的，检查全部通过就算完成；回答问题的，事先定好判定规则和预算，结论是"否"也算完成。
- 每个里程碑做一次端到端验收，专门防止"局部完美、整体断开"。
- 循环只留在单个 Change 内部，沿用 Converged / Stalled / Unreachable 三种出口，并设次数上限。

## 0. 结论先行

Owner 问："做着做着发现方向有问题，是改 spec 还是改什么？"

**回答：先判断问题出在哪一层，只改那一层。哪一层被改了，依赖它的部分就自动失效，重新验证；没被依赖的部分不动。**

为了让这件事做得到，完整版的核心是一句话：

> **意图是源码，计划是编译出来的，进度是算出来的，变更是一条差分。**

落到使用上，任何时候都能回答三个问题：
- 还差几项？
- 刚才改了什么，改在哪一层？
- 这次改动由谁批准？

调研中，没有一家公开方案做到"改了一条需求，只让依赖它的任务和测试失效"，也没有一家给出"交付之后改方向"的明确流程（见 research/02、05）。这正是 Ultra 历代失败的地方，也是完整版最有机会建立辨识度的地方。

## 1. 历代问题归纳成五个病根

| 病根 | 表现 | 出处 |
|---|---|---|
| ① 意图 → 规格 → 验收 → 代码，这条链会断 | V1 局部完美、整体断裂；1→100 越改越乱；北极星改了，没有机制重跑受影响的验收 | research/01 §C |
| ② 完成和进度由模型自己宣布 | task 的 status 由模型写；原生 `/goal` 的评估器只读对话记录，不运行命令，状态栏没有"N 项中的几项"（**已核实**，code.claude.com/docs/en/goal.md）；勾选复选框不等于完成 | research/01、02、03 |
| ③ 变更没有分层 | V1 的 Dual-Write 曾把变更分成扩大、纠正、缩减三类，缩减要 Owner 批准；后来变更记录被拆散，这套机制就丢了；V2 只改 Change 和北极星 | research/01 §B、§C |
| ④ 结构熵没有持续清理 | 文档漂移；静默失败（hook 被删一个月没人发现）；阻断式 hook 逼代理去改测试和 spec 来绕开 | research/01 |
| ⑤ 机制先于产品，拼装缺乏仲裁 | V2 在 22 天里两次大改版；八步计划的第 6–8 步关不掉；多个 skill 同时注入互相冲突的"下一步"，没人裁决 | research/01、Marketplace RESULT §1.3 |

需要更正 9 月诊断里的一个说法："完成全由模型说了算"说过头了。Change 层一直有可以运行的验收命令，`ultra-dev` 也有三种出口。真正缺的是 task 层的检查、Owner 能看到的进度，以及分层的变更机制。

## 2. 业界已经收敛的做法，和没人解决的事

**多数来源一致认可的做法**（这里只列已收敛的；分歧点见 research 各篇）：

1. 状态存在文件和 Git 里，交接也通过文件，不靠对话（03、04）。
2. 完成由外部检查判定，不靠自报；"未知"不算通过；派生出来的计数本身也要有测试（02、03）。
3. 有一份带编号的有限清单作为分母。例如 Anthropic 一开始列出 200 多条 `passes:false`，代理只能把它们翻成 true（03）。
4. 每次循环只做一个单元，每个 worker 用新的上下文；简报写清目标、输出格式、可用工具和资料、边界（03、04）。
5. 写操作只有一个写者。可以并行的是读、审查、测试。合并时校验 expected head（04）。
6. 规划者不写代码；worker 每次只做一项，做完交接。Cursor 删掉了 judge 和 integrator 这两个单点（04）。
7. 用稳定 ID 串起需求 → 任务 → 测试；每份计划都复制一遍全局约束；最后对整条分支做一次评审（02）。
8. 先过机械门，语义评审兜底；执行前检查计划结构，缺验证项就不执行，例如 pstack 的 `check-plan.mjs`（05）。
9. 协调交给模型，门禁交给脚本（05，与 Ultra 原有的"事实机械化，意义交给模型"一致）。
10. 持续对抗熵：维护黄金原则，后台代理开小 PR 修正偏离，有人专门打理文档，把复盘中暴露的机械错误改成确定性检查（03、05）。
11. 流程的重量随规模缩放。每个 harness 部件都写明它在补偿模型的哪个弱点，并且能一次拆掉一个；宿主补上了某个能力，就删掉自己对应的部件（02、03、05）。
12. 方法的进化采用"先暂存、再采纳"：配对评测，事先写好门槛，测试集封存，被拒的候选进入账本（06）。

**没人解决、而且正好是 Owner 痛点的事：**
- 交付之后改方向的明确流程，以及改动后的自动失效级联（02、05）；
- 从 0→1 到 1→100 的状态衔接（05）；
- 需求级的 N/M 进度。目前只有 OpenSpec 有一个 artifact 级的计数（02）。

## 3. 核心设计

### 3.1 项目真相分五层（回答"改哪里"）

| 层 | 内容 | 谁能改 | 改了以后 |
|---|---|---|---|
| **L0 方向** | 北极星、为谁做、成功与放弃条件、边界、"优雅"在这个项目里指什么 | 只有 Owner | 重新审视受影响的里程碑和需求 |
| **L1 行为规格** | 带稳定 ID 的需求，每条附验收检查 | 新增和修改：规划者起草，按"裁决"记录；**删除或缩小：必须 Owner 批准**（找回 V1 的 REDUCTION 门） | 关联的检查和任务标为"过期"，重新验证后才算数 |
| **L2 设计** | 设计决策（ADR）和架构不变量，每条不变量都有检查 | 规划者；里程碑处汇报给 Owner | 受影响模块的实现节点失效；不变量由机器持续检查 |
| **L3 计划** | 任务图：节点、依赖、覆盖哪些需求、作用范围 | 由前三层编译而来，模型可以自由重排 | 只要分母变了，就写进计划日志，所有人都看得到 |
| **L4 执行** | 节点内部的实现细节 | 写者 | 不往上传 |

### 3.2 变更怎么走：上报阶梯

worker 在执行中发现问题时，必须先判断问题属于哪一层，不能自己改验收去绕过：

1. 只是我的实现有问题？→ 在节点内重试（L4），最多 3 次。
2. 方案或模块设计走不通？→ 报到 L2：规划者修改 ADR 或接口，受影响的节点失效。
3. 验收本身错了，或者需求之间矛盾？→ 报到 L1：起草规格差分。新增或修改按"裁决"自行决定，删除或缩小必须交 Owner。
4. 方向或成功标准有问题？→ 报到 L0，只能由 Owner 决定。

凡是模型自己做的决定，都记一行"裁决"，格式借鉴 Superpowers：

`裁决：<决定> — 因为 <理由> — 如果判断错了，代价是 <代价>`

Owner 事后看的是这本账，不用一路被问。

连续两次修复都失败，而且失败指向同一个前提时，先检验这个前提，再决定往哪一层上报（借鉴 pstack 的 Attack the Premise）。

### 3.3 任务图加三种循环（回答"graph 还是 loop"）

两者都要，各管一段：

| 循环 | 时间尺度 | 停止条件 |
|---|---|---|
| **节点循环** | 分钟到小时 | 实现 → 跑检查。出口是已收敛、停滞、走不通三种之一，有尝试次数上限；停滞时按上报阶梯处理 |
| **里程碑循环** | 天 | 沿着任务图的前沿逐个做节点；每合入一个节点就跑全量回归（棘轮）；每 K 个节点安排一次清理。所有需求变绿，加上端到端旅程通过、整分支评审、Owner 演示，才算结束 |
| **方向循环** | 按需 | 由 Owner 或上报触发。L0/L1/L2 出现差分 → 失效 → 重新编译任务图 → 分母变化，并写进计划日志 |

两层循环设计稿里"大循环不做计划"这一条，由"里程碑任务图"取代。设计稿里好的部分全部保留：小循环等于一个 Change；循环之间只通过文件耦合；Frozen/Firm/Fluid 分层；评判按层分工。

### 3.4 进度：每条需求只有五种状态

| 状态 | 含义 |
|---|---|
| 绿 | 当前 HEAD 上，关联检查全部通过 |
| 红 | 有检查失败 |
| 未知 | 检查跑不起来，不算通过 |
| 过期 | 需求在上一次通过之后被改过 |
| 未覆盖 | 没有关联检查，不算完成 |

进度行由引擎计算，模型不能手写，例如：

`M2 · 9/14 绿 · 2 过期 · 1 未知 · 下一项 N-07 · 本里程碑计划变更 3 次`

计数器本身要有测试，吸取 GSD 1.42.1 计数静默回退的教训。

### 3.5 上下文切割：按节点编译

每个节点拿到一个上下文包，有预算上限，只装这些：

- 节点简报：目标；所覆盖需求的原文；需要变绿的检查（只读）；作用范围；不能碰的部分；什么时候上报；交接格式。
- 按路径匹配的不变量。
- 相关的 ADR。
- 依赖节点的接口签名，以及它们的交接记录。
- 这一片区域的教训（Firm 层），只取前几条。

不倒入整份规格，也不装原始日志。AGENTS.md 和 CLAUDE.md 控制在大约 100 行，只当导航地图（OpenAI 的做法）。hook 只给指针。超长的输出写进文件，正文里只留一行 grep 得到的 ERROR。

### 3.6 角色与多 Agent（回答"Codex 和 Claude 怎么平衡"）

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 访谈者 | 0→1 阶段把意图问清楚：一次一问，事实和决定分开记 | 不写规格以外的东西 |
| 规划者 / 架构师 | 写规格、写 ADR 和不变量、编译任务图、分诊上报 | **不写代码** |
| 验收作者 | 把 Owner 用人话说的"怎么算做到"翻译成检查 | 不实现功能；写者不能修改这些检查 |
| 写者 | 一次只做一个节点，用新上下文，走 TDD，交出交接记录和证据 | 不改验收，不跨出作用范围 |
| 验证者 | 机器跑检查；对机器证明不了的部分，用干净上下文评审 | 不看写者的推理过程 |
| 清理者 | 对照黄金原则扫描、打理文档、复盘，并把发现变成新的检查和清理节点 | 不直接做大重构 |

合并门是机械的：校验 expected head，跑全量回归，红了就二分定位。不设单独的 integrator 角色。

关于多 Agent 和跨厂商，研究证据很弱，我们自己的 Factory 数据也没有显示稳定收益，所以：
- **默认只有一个写者。**
- 只有任务图前沿上同时有 ≥2 个作用范围不相交、而且分量够大的节点时，才并行，用 worktree 隔离。
- 读、审查、测试可以随时并行。
- Codex 和 Claude 的分工按实测决定，而不是按偏好：大批量的实现可以交给 Codex（额度），规划、验收和评审放在另一侧。跨厂商评审是否值得，用 A/B/C 三组实验来判定：
  - A：单写者；
  - B：A 加上并行的只读探索和测试；
  - C：B 加上跨厂商评审。

  每个单元都分别记录等待时间、上下文重建、返工、合并冲突、花费。之前的 Factory 定位不出慢在哪里，就是因为没记这些。
- 无人值守运行用 workflow 脚本或 SDK、`codex exec` 会话，不用 agent teams。文档写明 agent teams 在非交互模式下不会派生 teammate；这一点是文档依据，还没有实测。

### 3.7 防熵：让 1→100 越改越整齐

- **棘轮**：历史上每条需求的检查都永久留在回归里。只有经 Owner 批准的缩小，才能把检查移出。
- **不变量**：每条不变量都对应一个机器检查，报错信息里直接写修复办法。
- **清理节点**：每 K 个节点做一次，里程碑结束时再做一次。清理只产出小节点放进任务图，不直接动手大改。
- **复盘**：同一类机械错误出现两次，就变成一条新检查，只改环境，不改代码（mattpocock 的 retro）。教训在 Fluid 层重复出现、而且有证据时，才升到 Firm 层。
- **会话开场仪式**：先读状态和 git log，跑一遍端到端冒烟测试，再开始新工作。
- **验收受保护**：写者不能修改检查和评测器。可以恢复的问题只给提示；只有不可逆的操作才真正阻断（吸取 V1 阻断式 hook 的教训）。

### 3.8 方法自进化（回答"多套方案怎么改版"）

分两种速度：
- **项目知识**：每个 Change 都可以改，Git 就是演进轨迹。
- **方法本身**（Ultra 的剧本、提示词、门槛）：只能以候选的形式进入。

候选方法的流程：

1. **观察**：保留失败时的原始输入、输出、检查日志和版本号。
2. **提案**：每个候选只改一处，并写明"在什么情况下可以推翻它"。
3. **配对评测**：在冻结的开发集和门槛集上，候选和当前版本配对运行至少 3 次。先跑一次 A/A（同一个版本跑两次），估计噪声有多大。
4. **事先写定的门槛**：差值必须超过噪声带，再加上一个预设的最小增益；每类任务都设回归上限；胜出的候选还要在新的一批任务上复测一次。
5. **封存测试集**：只在这里报告一次，不参与任何选择。
6. **采纳和回滚**：由 Owner 采纳，打 Git 标签；回滚就是回到上一个标签。被拒的候选连同改动、每项得分和拒绝原因记进账本，提供给下一轮提案参考（借鉴 WikiSkill 的 skill-impact 记录和 SkillOpt 的 rejected buffer）。

多套方案并存时：
- 每套方案都作为有名字的变体保留；
- 只有在某一类任务上通过门槛，才按这类任务路由给它；
- 不把几套方案混着用。

**拆除也是进化**：模型或宿主升级之后，一次只拆一个部件，用同一个门槛检验（Anthropic 的做法）。

**统计上要诚实**：要分辨 62.5% 和 25% 的差距，每组大约需要 27 道题。小样本只能看出很大的差异，大多数候选的结论会是"未证实"，这时默认版本不变。第 8 步那组 5/8 对 2/8，p ≈ 0.315（**已核实**），维持拒绝。

**一个 Alpha 候选：工程样本就是基准集。** Owner 要"真实、优雅、厉害的工程样本"。每个样本的里程碑和验收检查，就是方法进化的冻结评测任务。展示品和回归基准是同一件东西。

### 3.9 Owner 在哪里介入

| 时机 | Owner 做什么 |
|---|---|
| 0→1 访谈（重，可以接受） | 确认北极星、里程碑切分，用人话确认每条需求"怎么算做到" |
| 里程碑门 | 看演示、端到端结果、规格差分汇总、裁决账，然后放行或改方向 |
| 上报 | 只处理 L0 和"删除或缩小"两类 |
| 随时 | 看进度；插话会作为 L0 或 L1 的差分进入系统 |

其余全部自动进行，每个决定都记一行裁决。

## 4. 产品形态：一个完整体

**一个入口**（`/ultra` 或 `ubp`）。它读状态，确定性地决定下一步做什么，解决多个 skill 抢着注入"下一步"的问题。完整版由四部分组成：

1. **引擎**：确定性代码，规模要小。负责：状态和进度计算、计划门、失效计算、检查执行与证据记录、上下文编译、合并门，以及给 Stop hook 用的确定性检查。代码量预算由 Owner 定，我建议不超过 2,000 行（不含测试）。可以复用 ultragoal 的 `validate_artifact.py` 和 `ultra-delegate` 中合用的部分。
2. **方法**：面向模型的指令，对应访谈、规格与验收、规划、写、验证、清理与复盘、变更分诊这几段。它们是同一个产品的内部阶段，不是互相引用的独立 skill。Marketplace 上那三个 skill 继续单独发布，可以作为素材。
3. **适配器**：先做 Claude Code 和 Codex。Claude Code 侧包括 SessionStart 指针、Stop hook 确定性检查、状态栏或 mod 面板；Codex 侧包括 AGENTS.md 地图和 hooks。其他宿主以后再加。
4. **视图**：终端一行进度；由文件生成的 HTML 进度页；Claude Code 状态栏。

**保留**：
- 文件是权威，Git 是演进轨迹；
- 打开 Change 之前先读归档；
- 三种出口；
- 一次只问一个问题的访谈；
- Owner、模型、机器三方的分工。

**从 V1 找回**：
- 变更分类和缩减门（Dual-Write），对应 L1；
- 计划与开发之间的审计（`/ultra-analyze`），对应计划门。

**移出主路径**：
- Factory 机制（W3 IPC、durable grant、唤醒）。代码保留，但默认不走。
- 六宿主对齐。
- 每个 task 跑六种评审。
- 每次工具调用都重新注入。
- 8 MiB 的注入上限，改为真正的上下文预算。

## 5. 落地阶段

每个阶段都以可观察的结果作为出口，而不是以"机制完整"作为出口。从 P1 开始，各阶段的进度都由引擎自己计算。

| 阶段 | 内容 | 出口（可观察） |
|---|---|---|
| **P0 收尾与决定** | Owner 关闭八步里的第 6–8 步；选定样本项目；确认核心模型 | 决定写进 `.ultra/decisions/` |

## 6. 风险与反对意见（自查）

1. **最大的风险是又去造机制。** 这件事历史上反复发生。对策：每个阶段都以样本的结果出口；引擎有代码量预算；上一阶段的出口没有被观察到，下一阶段不开始。
2. **追溯成本和规格过重。** 需求的粒度定在"用户可观察的行为"；小修小补直接落在 L4；流程的重量随改动大小缩放。教训来自 Kiro：修一个小 bug 也要写一堆文档，以及 OpenSpec 的 MODIFIED 噪声太大。
3. **验收质量。** Fowler 认为 AI 写的测试"还不够好"。对策：Owner 用人话确认验收；验收作者不是写者；验收受保护；关键需求要做一次强制变异，确认检查真的会失败。
4. **失效的精度取决于链接。** 链接用显式 ID 写在测试和节点里；计划门双向检查覆盖；"未覆盖"和"未知"都不算完成。
5. **"优雅"无法用机器检查。** 在 L0 写明这个样本对"优雅"的定义，再由不变量、黄金原则、整分支评审和 Owner 演示共同把关。
6. **宿主功能会变。** 文件是权威，适配器保持薄，每个部件都能单独拆掉。
7. **反方观点：照 GSD 那样做就够了。** GSD 没有失效机制，也没有 1→100 的路径，而这正是 Owner 的痛点。GSD 在简洁上的经验（删掉代码智能子系统、删掉重复的提示副本）照单吸收。

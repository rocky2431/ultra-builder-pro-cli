# Trellis 与 Ultra：结构对照、演进方向与实施计划

2026-09-08。Codex 与实际 Claude Code 完成三轮讨论后，Owner 表示认可方向，并要求具体步骤、各步效果和最终效果。本文保留结构研究，后半部分给出八步实施计划。方向认可不代表本计划所有细节已获接受；当前只交付计划，原实施继续暂停。

## 建议

保留 Ultra 的产品与已有权威结构，借鉴 Trellis 把项目知识、当前任务、执行和经验回写连接起来的方法。优先完善普通开发的实际路径，同时保留完整软件工厂目标。当前不建议整体换成 Trellis 底座，也不建议直接继续堆完 B/C/D/E 后才检验日常价值。

核心原则是：固定意图保真、真实交付和恢复这些承诺，让具体方法随任务调整。用户表达结果与业务取舍，Agent 负责技术调查、上下文整理、内部路由和已授权的连续推进。

“属性”暂按产品主张理解，未收到 Owner 更具体的定义。不能据此声称 Ultra 已有可验证的市场独特性。

## 两边实际结构

Trellis 检查快照：`88f4834449da9b4f607ec05e322408a0aa66f2ce`，CLI/core 0.6.16。分析的是发布模板与实现，不混用其仓库自用配置。

| 层面 | Trellis | Ultra 当前实现与目标 |
|---|---|---|
| 产品载体 | CLI 安装/更新，项目内 workflow、scripts、平台 hooks/agents；core 提供 task/channel/mem | 安装器与六宿主 adapters；14 Skills、5 可选 Hooks；已有委派边界复用 agent-delegation/ACPX |
| 持续项目知识 | spec 按包/层组织工程约定；workspace journal 留会话历史 | project brief、North Star、产品/架构 specs、CONTEXT、decisions、历史 Change |
| 当前工作 | 每任务 task.json、prd.md，可选 design/implement，以及角色 context manifests | Change intent、统一 tasks ledger、task context、验收证据、Review 和 Resume |
| 上下文 | 模型策展 implement/check.jsonl；Hook 推送或子 Agent 自读 | Skills 指导读取当前 context、相关决定与历史；Hooks 注入方向与当前验收等信息 |
| 执行与检查 | implement/check 子 Agent；check 可直接修代码；另有 channel 进程与消息运行层 | 主 Agent 或授权委派；独立审查、证据消费、集成与交付判断；完整 C/D/E 尚未实现 |
| 经验 | 完工时判断并更新 code-spec，供后续任务消费 | 已有历史读取、Pattern/Tech Notes 与文档维护；应检验经验是否及时进入后续执行，不能说完全没有学习 |

Trellis 的 [workflow 模板](https://github.com/mindfold-ai/Trellis/blob/88f4834449da9b4f607ec05e322408a0aa66f2ce/packages/cli/src/templates/trellis/workflow.md) 是 Plan→Execute→Finish；README 的 Verify 对应 Execute 内检查。其 [context 注入](https://github.com/mindfold-ai/Trellis/blob/88f4834449da9b4f607ec05e322408a0aa66f2ce/packages/cli/src/templates/shared-hooks/inject-subagent-context.py) 有实际代码，但只保证材料传递，不证明选择正确或模型理解。

[channel supervisor](https://github.com/mindfold-ai/Trellis/blob/88f4834449da9b4f607ec05e322408a0aa66f2ce/packages/cli/src/commands/channel/supervisor.ts) 确实持有 Worker 并桥接事件；其 [adapter registry](https://github.com/mindfold-ai/Trellis/blob/88f4834449da9b4f607ec05e322408a0aa66f2ce/packages/cli/src/commands/channel/adapters/index.ts#L194) 当前为 Claude/Codex。跨平台配置覆盖不能当作运行能力完全等价。

## 对交互与“属性”的判断

你对交互负担的批评有源码依据：小任务也被要求询问是否创建任务；[brainstorm](https://github.com/mindfold-ai/Trellis/blob/88f4834449da9b4f607ec05e322408a0aa66f2ce/packages/cli/src/templates/common/skills/brainstorm.md#L3) 即使意图已清楚，也要求最终规划摘要后再给一次实施批准；收尾还有 commit 计划与 finish-work。它同时明确要求 Agent 自查仓库事实，所以不是把所有思考交给人。

Trellis 并非没有主张：它强烈强调规划、工程约定与固定收尾。它的方法文件在项目内可调整。Ultra 更强调长期产品意图、证据与权威、模型自主判断和可恢复交付。两者是重心差异；Ultra 的主张更详细，不等于体验或结果已经更好。

## 应如何继续

1. **检查入口与路由的实际可达性。** 明确小改复用已有意图；模糊新产品需要研究真实用途。不能全局把 Research 换成编码。已有简单分支若从未被看到，修入口/加载；若被考虑后错误拒绝，才修路由。Stage A 已做紧凑进度和取消无条件重问，不再包装成新功能。
2. **让当前任务带着相关项目知识进入实现与检查。** 优先用现有 context 的 Pattern、Tech Notes 和引用，复用项目已有文档。只有实际漏读的证据支持时才补注入；不先加另一份 manifest 或知识权威。
3. **在学到事实时维护原文，在需要时消费。** 项目事实与已接受约定的维护属于当前授权工作；尽量在最终审查前完成必要更新。新策略是否以后默认采用，仍是候选评测与 Owner 晋升的问题。不要每个小任务强制产出七段 spec。
4. **普通开发与工厂能力按真实路径推进。** 当前会话能做的工作不必等待未调用的 Worker 路径资格；但不能借此宣布 D1、并行或跨会话恢复通过。B/C/D/E 保留各自未完成状态与退出条件。

例如“修 CSV 中文乱码”：Agent 自查和复现，判断与已有承诺的关系，选择相称验证，交付实际修复及限制。用户不操作 mode，也不必为纯内部步骤再批准。正式 Change 的交付声明仍按其合同处理。

例如“想做本地读书笔记工具但还没想清楚”：先问用途——阅读时快速记录，还是日后查回出处；技术排序由 Agent 判断。原型只有在回答明确不确定性时才有意义，不替代完整产品目标。

## 三轮如何改变了结论

- 第一轮独立查看：CC 偏重新增约定回流与按效果拆资格；Codex 同意经验消费值得借鉴，但反对新知识库和未经证明的隔离捷径。
- 第二轮交叉检查：撤回“Ultra 无学习”、固定六 lens、零可改性、行数阈值。CC 有效指出统一视图可能只是重复 A；Codex接受，转向检查真实消费与路由。
- 第三轮收敛：撤回没有合法知识写者、底座绝对不可行、两轮问答即可判好用和含糊产品先写代码。双方支持当前建议，仍无法仅凭源码区分路由、可达性、上下文和收尾谁主导成本。

实际三轮分别为 `9f73a151f5954929a8fc3d9fd5baeefc`（606.596s）、`8c889ccf89a5401492fec7a61504e8df`（265.832s）、`99f729bda39647ec84f2450c5af7c0b6`（147.520s），均 success/end_turn，同一 Claude 原生会话续谈。首轮没有读取 Codex 初步立场，后两轮交换了论点。共识不是独立实测。

## 结构研究的下一步及限制

建议下一步选择新的明确小改、模糊新项目、跨会话迭代请求，复用现有评测方法，定位上述消费路径。记录质量、必要问题遗漏、错误完成、恢复、Owner 投入、总耗时与成本；少提问、少文件只是诊断信息。先改一个证据支持的真实路径，再根据结果扩展；不重跑已验收 A 的原旅程，也不再造评测框架。若现有行为已经好，就不改；若原因不明，保留不确定性，不以讨论代替证据。

目前不整体采用 Trellis：当前没有证明迁移后的权威、运行保障与使用收益值得替换现有实现；直接叠加会重复任务状态与运行层。这是有条件的选型建议，不是证明任何迁移都不可能。

结构研究未运行 Trellis 安装或产品命令，未测量生产率、知识复用收益或真实交互可靠性。未修改产品代码，未安装、提交、发布。Owner 后续已认可方向并要求以下详细计划；原实施继续暂停。完整修订记录见 [THOUGHTS.md](./THOUGHTS.md)。

## 详细实施计划：八步、三个可用里程碑

### 最终产品效果

Ultra 的目标是一个能理解产品意图、使用项目积累、持续推进并可信交付的开发工作流与软件工厂。Owner 用自然语言表达目标、约束和业务取舍；Primary Agent 负责技术调查、方法选择、上下文准备、执行组织、集成与结果判断。清楚的小改能直接推进，模糊的新产品能经过有终点的讨论形成方向，已有项目能在连续迭代中保持整体一致。

项目已有的工程方法可以调整，产品意图和已接受的承诺始终可追溯。工作产生的可靠事实进入下一次执行；策略改进经过比较再采用。适合分工的任务可以使用实际合格的 Agent 协作，复杂长任务在明确授权和预算内具备可撤销的持续运行能力。

保留独立 CLI 的产品方向：公共入口承担可发现的运行、观察、停止和恢复操作，宿主模型继续承担语义决策，复用现有跨 Host 适配和委派能力。未来 PaaS 是部署形态延伸；租户、计费和生产平台不列入本轮八步的完成条件。

| 步骤 | 本步交付的能力 | 用户可感知的效果 | 依赖 |
|---|---|---|---|
| 1 | 明确行为目标、实际加载基线与问题位置 | 后续修改有具体对象，不重做已完成的体验整改 | 现有研究与 Stage A 证据 |
| 2 | 自然语言进入相称的开发路径 | 清楚的请求直接推进，关键业务歧义才需要讨论 | 1 |
| 3 | 项目知识进入任务，任务事实回到项目 | 不必反复解释约定，后续工作能正确利用前面所得 | 1；沿 2 的实际路径接入 |
| 4 | 日常开发、持续迭代和显式恢复的完整验收 | 得到第一个可日常使用的连贯版本 | 2、3 |
| 5 | 合格委派与首条真实工厂闭环 | 一个有分工价值的任务能自动协作、修复并交付 | 4；内部先完成 B 再进入 C |
| 6 | 多轮、多任务形态与多 Profile 的稳定运行 | 能持续迭代，并正确决定何时独立做、何时分工 | 5；对应 D |
| 7 | 受控跨会话续跑 | 关闭当前会话后，已授权工作仍可正确恢复 | 6；对应 E 的耐久部分 |
| 8 | 经评测的策略改进与回退 | 工作流有证据地改进，Owner 能理解、接受或拒绝变化 | 6 的真实记录；与 7 分别验收 |

三个里程碑：步骤 1–4 为“日常开发闭环”；步骤 5–6 为“可运营的软件工厂”；步骤 7–8 为“可持续运行与受控改进的完整目标”。前一里程碑使用相同意图、证据与恢复含义累积扩展，不制作之后要推倒的一次性原型。

### 第一步：把认可的方向变成行为目标，定位真实缺口

具体工作：
- 以当前已验收 Stage A 为基础，记录 checkout、未提交来源、隔离生成的安装件和实际加载版本。保留未接受的 B 工作与历史失败，不用一个混合工作区的成功替代某个版本的验证。
- 从现有旅程方法中选择新的三类请求：明确小改、模糊的 0→1 产品、已有项目的跨会话迭代。第一批建议每类两个案例，一个用于定位和修复，一个预留作未参与调试的检查；这是计划建议，不是统计充分性的声明。
- 检查从请求进入 Skill、路由、上下文读取、执行、检查、收尾的真实过程。每个问题区分为“没有加载正确入口”“模型选错路径”“缺少相关材料”“材料已有但没用”“完成过程反复失效”。只有能改变修复的未知继续调查。
- 在既有评测记录里写清完成行为和对应证据。已经正常的路径保留，不因阶段名称而强制改动。

预期效果：得到一份有来源的最小修改清单，明确每项改变要改善哪种用户行为。避免将 Stage A 已实现的取消无条件重问、紧凑进度表达再次包装成新功能。

验收：三类请求均有当前行为记录；每项计划修改关联实际问题或已确认的新需求；无法区分的原因保留为待验证假设。该步到足以选出首个修复就结束，不重开 Trellis 选型和三轮讨论。

### 第二步：让 Agent 承担日常流程选择

具体工作：
- 修复第一步确认的入口、加载或路由问题，让明确自然语言请求能到达已有的相应工作路径。
- 明确小改先调查、复现和修复；涉及新产品承诺或关键用途时进行针对性澄清；普通技术事实由 Agent 查，不把仓库能回答的问题推给 Owner。
- 在已覆盖的任务与授权中连续推进，保留原有正式 Change 与微改的真实含义。微改可以报告实际修复，但不能伪造正式 Change 的 Review、Test 或 Deliver 完成。
- 复用现有进度和恢复表达。只在结果、重要变化、可行动阻塞和必要决定处增加有用信息。

主要入口：`skills/ultra-change/`、`skills/ultra-init/`、`skills/ultra-plan/`、`skills/ultra-dev/`、`skills/ultra-research/`、`skills/ultra-status/references/route-contract.md`；只有观察证明加载问题时才改对应 adapter 或 Hook。不是预授权修改全部这些路径。

预期效果：Owner 说“修 CSV 中文乱码”，Agent 能自己查清问题并交付修复；Owner 说“做一个本地读书笔记工具”，Agent 会先解决用途与结果的关键歧义，而不是要求 Owner 选择内部 mode。

验收：明确请求不新增内部流程审批；重要业务问题没有漏问；不扩大原请求；修复真实生效。继续使用现有 Review 和授权合同，若合同本身被证据证明需要变更，显式提出对应变更，不靠隐藏输出绕过它。

### 第三步：接通任务上下文与项目知识的往返

具体工作：
- 实现前，Primary 从现有项目文档、相关决定、相邻代码和历史 Change 中选择与任务有关的材料，填入已有 task context 的 Pattern、Tech Notes 和引用。
- 让实现与检查各自拿到必要材料：实现需要可复用代码与约定；检查需要目标、关键约定和当前验收。避免全量注入所有历史。
- 学到新的可靠事实、修正已过时文档时，维护现有权威原文并保留出处；任务专有的临时结论留在当前任务，不自动变成长期规则。
- 必要文档更新尽量在最终检查前完成。更新导致已有审查或测试失效时，刷新受影响证据；不为减少收尾次数而降低证据要求。
- 对改变产品承诺的知识修订，走已有 Owner 决定；对跨任务行为策略的变更，留到第八步评测。

主要入口：`.ultra-template/contexts/TEMPLATE.md`、`skills/ultra-plan/`、`skills/ultra-dev/`、`skills/ultra-review/`、`skills/ultra-deliver/`，以及项目已有 `CONTEXT.md`、specs、decisions 和历史 Change。优先改实际消费指令；自动注入只针对实测漏读增加，不先建新知识库或第二套上下文清单。

预期效果：前一次任务确认的字段含义、测试约定或接口限制，后一次任务能正确应用，Owner 不用再次说明。无关经验不会变成每个任务的负担。

验收：一条实际前后任务链证明“发现事实→维护原文→新会话读取→后续实现/检查正确使用”；另有过时、冲突或无关材料的反例，证明系统会核对和筛选。文件被读取只能证明传递，最终行为正确才证明消费。

### 第四步：交付并验收完整的日常开发体验

具体工作：
- 在隔离的生成安装件上，走通新项目从用途到实际可用成果、已有项目连续修改、明确小改、任务切换及用户显式要求的中断恢复。
- 补齐相关公共说明与例子，用目标语言展示怎么用；不要求用户学习内部证据格式。检查当前支持 Host 的安装/生成兼容性，分别记录真正跑过的 live Host。
- 由未参与对应实现的验收者操作最终成果，核对原始用途、修改后的整体路径、知识利用与恢复正确性。
- 与第一步基线比较 Owner 主动投入、必要问题遗漏、重复解释、实际结果质量、错误完成、总耗时与成本。固定可比的任务与模型条件，保留失败与人工帮助，披露小样本限制。

预期效果：第一次交付一个日常可用的 Ultra 版本。Owner 能启动、迭代、停下并要求续接；连续修改仍围绕同一个产品目标。

验收：选定旅程的行为标准全部有当前证据；没有未处理的关键遗漏或虚假完成；已证实的体验缺陷消除，质量和恢复不退化。成本改善只报告实测范围。这里的恢复依赖用户发起新会话或明确续接，尚不宣称后台自行唤醒。

对应代码变更按仓库要求完成窄验证、`npm run verify:release`、`npm pack --dry-run --json`、只读全 Host doctor；改动 Skill 用 Skill Creator 验证，manifest/marketplace 改动才增加相应插件验证。安装测试使用隔离配置目录。通过后可交付安装候选；真实 HOME 安装、commit、发布和部署按各自授权执行，不由“日常版本通过”自动触发。

### 第五步：闭合委派前置，跑通第一条真实工厂交付

这一阶段有两个不可混淆的出口：先完成旧 Stage B，再完成 Stage C / R2 Step 1。

具体工作：
- 恢复 B 前实时核对 UBP、agent-delegation、相关隔离工作树和原生 runtime；依赖已有并行更新不能按旧版本假定。先复验已交付修复，再对选定 Host 做同强度正向资格，消费 Task Review、aggregate 和实际 Test/Deliver。
- 资格既验证合法工作可用，也验证越界行为被真实限制；不能通过删除 Bash、假回调或未合格回退获得假通过。
- B 接受后，复用 agent-delegation/ACPX 运行有限任务片段。Primary 决定拆分、角色、依赖和后续动作；运行层负责启动、等待、取消、结果与恢复事实。
- 在公共 CLI 的现有入口与消费者上接通实际运行、观察、停止和恢复，具体命令名在源码设计时确定，不先新增一套控制系统。
- 选择有实际分工价值的产品任务，让至少两个写入范围不重叠的真实 Worker 执行时间重叠；Primary 集成，并处理一个真实可复现的失败，修复后重新验证最终结果。

预期效果：Owner 给出一个可执行目标后，Ultra 能完成有意义的分工、等待、集成、修复和交付，不需要 Owner 手动搬运各 Agent 的结果。

验收沿用既有标准：合格 W1 与所选 Host 的 W2；等待期间 Primary 无空转模型轮询；真实并行；最终集成版本的 E2E；fresh independent Review；取消、重启和 unknown 场景不重复启动 writer；形成 owner-visible `delivery_ready`。与公平 Solo 基线比较并保留实际协调成本；一条成功路径不等于整个工厂完成。

### 第六步：从一条闭环扩展到可运营的软件工厂

具体工作：
- 在同一意图与合同下支持多轮执行、分阶段依赖、局部失败和集成返工；保留成功产物，按当前证据调整下一片段。

预期效果：从一次演示变成可重复的开发方式。跨多个迭代仍能接续产品目标，分工只在有价值时出现。

验收沿用 D / R2 Step 2：至少两个不同任务形态、两个 qualified Profiles 重复成功；正确选择不并行；多轮修复有边界；W3 消息丢失、重复和会话死亡被正确处理；在适合的任务上相对 Solo/Step 1 出现可重复收益。没有收益的配置保留限制或不启用，不靠增加 Agent 数量证明进步。

### 第七步：实现受控的跨会话持续运行

具体工作：
- 在第六步稳定的合同上加入最薄的运行生命周期支持，复用已有事件、结果、Resume 与权威引用。

- 检验进程退出、机器重启、网络失联、重复通知、旧 writer 未知、授权到期/撤销和任务输入变化。
- 有意义的完成、失败或需要 Owner 决定时通知；正常未变化状态不要求 Owner 反复查询。

预期效果：Owner 不必为了长任务保持原聊天会话一直打开。系统能在授权范围内继续，遇到边界变化会准确停下并说明需处理的事。

验收沿用 E / R2 Step 3 的耐久标准：在 Primary 与 Supervisor 均结束后真实恢复；过期和撤销在重启边界仍生效；同一事件不重复产生语义动作或 writer；未知状态如实恢复。用户手动点击续接、旧进程一直存活或 API 回显成功都不能替代这项证明。

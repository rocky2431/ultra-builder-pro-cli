# Stage A independent review and observation method

This is Codex's review method, not an implementation instruction or a claim of passing results. Baseline: `2e3273bf12f6493b3201fad3d9d1b802ae367a4f`. Freeze the returned ZCode candidate and record exact loaded source before provider evaluation. Keep all attempted runs, including failures.

## Decision and result observations

Use three product paths from the accepted plan. Run actual Agents against the same initial facts, usable artifacts and acceptance when comparing baseline and candidate. A scripted Owner decision replay must be identified as such; it cannot measure real human active effort, comfort or willingness to continue. Do not substitute source-text assertions for these runs.

1. New project: a local list/filter/export tool for a person who currently searches a spreadsheet. Distinguish the requested useful outcome from a prematurely chosen app architecture. Preserve supplied local-only/data constraints. Clarify only unresolved choices that change the first usable result, then actually reach and verify that result.
2. Existing project: a precise label or filter change with explicit input, followed by a cross-module export requirement. The precise first edit should not require reapproval of the same clear answer. The later change must expose and resolve any genuinely unsettled data/export semantics, then preserve the original product path after integration.
3. Brownfield takeover: reproduce a filtering/export mismatch with special characters and empty data before repair. Reachable implementation facts belong to the Agent. Missing business intent remains a real decision, and an unverified implementation must not be called complete.

For each run preserve the provided facts and Owner answers, actual clarification requests, new/repeated decisions, loaded version, first usable output, targeted and whole-path checks, semantic gaps, recovery, false completion/refusal and observed elapsed time. Where necessary decisions are intentionally absent, the correct result may be a concise pending question; where an answer is provided, verify that the next step uses it. Missing cost or human activity data remains unknown. Count justified and repeated questions separately, with transcript references supporting each classification. Conclusions apply to these cases only.

## Hook boundary observations

Exercise ordinary inactive use, a current task, repeated calls, changed acceptance, task switch, fresh/recovered session and unavailable session identity through actual registered adapters. Verify the rendered Host output as well as shared-function output. Inspect malformed or unwritable disposable-cache behavior and separate reminders from diagnostics and authorization. A suppression cache cannot provide authority or suppress first delivery to a new lifecycle identity.

A baseline observation to resolve: `adapters/zcode.js` registers mid-workflow recall for PreToolUse, while `hooks/adapters/zcode.py::adapt_output` projects a shared PreToolUse additionalContext-only response to `{}`. Reproduced by directly calling the baseline adapter. Determine the actual documented Host contract and coverage before classifying this as supported behavior, a coverage limitation or a fix. Do not invent a permission grant just to make advisory text render.

## Acceptance and commit

Review the whole final changed path and every material finding against exact source and a proving command. Stage A code acceptance needs the relevant behavioral checks and actual-provider evidence, with no missing required decision or false completion. A claim of reduced real Owner burden requires actual Owner observations, not simulated interaction counts. Preserve any gap instead of promoting it to PASS. Codex, not ZCode, decides whether the stage is ready and performs the detailed commit.

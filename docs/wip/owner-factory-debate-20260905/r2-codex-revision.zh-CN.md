## 3. 运行层选型与 ACP 迁移裁决

**当前选择：以已有 UBP delegate-worker 边界为基础，补最薄的 RunSlice 执行/等待路径；暂不让 experimental ACPX Flows 成为生产必需依赖。** 理由是本地声明图执行没有已验证的原生 fan-out 与重启恢复，接入仍需厂内解决关键生命周期，且有 API 漂移。它保留为可替换候选，不把“无法原生表达”扩大成“任何 JS 包装下都不可能并发”。符合条件时重新比较，无需另建图引擎或数据库。[C13，ZCode/Kimi 第二轮源码核对](./evidence-codex.zh-CN.md)

迁移分工：agent-delegation 管通用注册、连接、会话、委派任务及原始 receipt；UBP 管当前任务输入绑定、环境隔离、工作区/效果、writer 独占、取消核对、集成与验收。若一次性 wrapper 缺事件/取消能力，只在其公开边界补实际消费者需要的薄接口；不把厂内语义策略下沉为通用 transport 规则。覆盖差异（UBP Grok / registry Hermes 等）显式盘点，不默认所有 Host 同级。

**failure_reason 不先变新必填枚举。** ACP 层原样留 stopReason、退出码和结构化错误；工厂 reader 根据版本明确支持的结构化码作可选分类，保留依据，未知就未知。自然语言由 Primary 解释给 Owner，不能驱动机械释放 fence。待现有字段被真实消费者证明不足，才版本化扩充公开结果合同，避免一轮讨论造第二套错误协议。

**第三轮必须正面检查的安全反例：** Kimi 第二轮 Q7 声称“环境净化 + writable_roots + 事后 diff 即可把 approve-all 限在围栏里”，这不成立。事后 diff 不能阻止已经发生的仓库外/网络效果；fence 管 writer 竞争，也不是 OS 沙箱。R2 §10.3 正因此要求真实 effect enforcement。也不能说 `--non-interactive-permissions fail` 让“任何权限请求”失败：本地 ACPX `live-checkpoint-Gw2oGjhe.js:2406-2440` 先匹配 policy/mode，approve-all 可先返回，仅需交互却无法交互时走 fail；`:2173-2175,3620-3622` 同样先处理 approve-all。合法能力须保留，危险效果必须由实际可达的 enforcement 边界控制；本次有人监督的 docs-only 研究不是无人值守资格证明。

## 4. 图怎么改、片段怎么接着跑

计划/Change 中保留目标关系与未来依赖；RunSlice 绑定当前版本，只含这次可执行的 attempts、依赖/barrier、边界和预算；可视图从这些材料派生。Primary 读 attention 后选择新片段；运行层不自行选择语义下一步。[R2 §5-6](../ultra-builder-pro-vnext-target-architecture-r2.zh-CN.md)

两类回路并存：节点内 Agent 可以探索、验证、修复；节点间实际证据可以使 Primary 拆分、合并、重排或换已授权方法。正在执行的 instruction/permission 输入不原地改；需改变时先处理旧 attempt 的停止与写者状态，再发新 revision。执行过的事实只追加解释，不覆盖成“没失败过”。

**部分失败：** barrier 的 required/optional、all/可提前失败，以及取消其他 attempts 的机械条件在发出片段时明确。运行层忠实汇报每个 attempt，不把一个失败变成整体成功；Primary 判断修复、重规划或提出范围修订。成功 sibling 可以保留工件；是否重用其验收，仍检查相关输入/依赖/当前 acceptance 与工件摘要。不是全量必重跑，也不是成功结果永远缓存。缺足够来源时重验受影响部分。

**执行器崩溃：** 不要求死掉的进程自己写终态。reader/recovery 从启动意图、worker 身份、receipt、fence 和当前存活事实重建观察；缺证据时 slice 派生状态为 unknown，禁止竞争写者。先利用已有每个 attempt 的持久材料，只补启动/结果消费之间的必要恢复记录，不先做通用事件仓库。测试必须覆盖 launch 前后及“效果已发生、终态未写”窗口。恢复不等于效果幂等。[C18](./evidence-codex.zh-CN.md)

| 原因证据 | writer 边界已证停止 | writer 活着或无法证明已停 |
|---|---|---|
| 正常 end_turn / exit 0 | 可读取并验证产物；仍不等于完成 | 不发布可信可替换终态，不启动竞争 writer |
| 协议失败/取消/有结构码的额度或认证错误 | 保留产物与恢复入口；按既有授权/预算处理修复或暂停 | 保留 fence，先核实停止/取消，原因已知也不放行 |
| 无协议终态、普通错误文字、执行器中断 | 可报告“已停止，原因未定”；核对效果后决定是否安全重试 | outcome_unknown；保留事实、尝试、未触碰项与恢复所缺证据 |

CC 那次仅有 exit 1、stopReason 空和额度文字，结构原因属于最后一行；本研究没有独立 writer-tree 停止证明，不能臆造右侧问题已关闭。要做人类可读解释，可以说“Host 提示额度限制”，同时保留机器可判原因 unknown。这是不同证据口径，不是装作没看见提示。

每个格子保留 receipt/mission/run/attempt/session 身份、输入 revision、已验证产物和下一项恢复检查。reader 可以重建未知状态；授权与 writer 身份必须独立核对。没有新权限缺口的修复无需每次问 Owner；需要改变目标、标准、预算或未授予效果时才询问。

## 5. 自进化的对象、证据和止损

任务内可直接改变产品代码、调查策略、下一片段的任务拆分/角色/依赖/委派指令。原始意图、必需验收、权限与已发生事实不被自我优化覆盖。跨任务可生成 Prompt、Skill、图模板、角色组合或运行组件候选，但持久默认行为需独立比较后按接受的晋升规则改变。

例：筛选 UI 与导出逻辑在集成时出现字段约定不一致 → 先补共享接口事实、修改下一片段并重验一致性。跨任务重复发生 → 提出“先做接口一致性检查，再分工”的模板候选；与当前模板、简单 Solo 基线在未用于优化的任务上比较。收益可以来自删除节点或减少 Review，不以变复杂为进化。

公开目标与验收标准；评估逻辑/基线哈希/原始记录放在被优化方不可写的可信边界，隐藏样本只能补充防污染。用于选候选的样本已属于开发反馈，不能又叫最终 held-out；按时间/来源外推并记录泄漏限制。验收器错误可提交反例、修正规则并重评，不能改旧失败记录“刷绿”。[C5/C6/C8/C10/C15](./evidence-codex.zh-CN.md)

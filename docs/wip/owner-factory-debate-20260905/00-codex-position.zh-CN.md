A2. 已有 acceptance 级四类证据，应该复用。命令退出码只能证明所执行检查的结果；Owner 意图、证据的充分性和外部事实需要各自对应的判断来源。

A3. Research 应先给出本轮决定边界、Agent 自查事项、Owner 待决事项和可观察退出。已回答问题跨调用复用；重新界定意图只在实质歧义或冲突证据出现时发生。

A4. 默认进度应呈现目标、当前位置、已验证结果、缺口、下一步和需要 Owner 的决定；内部协议细节作为可检查证据，不要求 Owner 承担调度和技术判断。

A5. Hook 重复注入与工作流验证是两个可独立调查的机制。没有证据支持“先增加 anchor 才能减少提醒”的必然顺序。

## 命题 B：自动化工厂的工作假说

B1. 产品定义是自动化软件工厂。目标工程中的访谈、边界、验收、carry-over、review、graph 可提供模式，但工厂还须拥有真实的执行、等待、集成、恢复、验证和交付路径。

B2. 图可以表达依赖、角色、输入输出和允许的回边；模型基于新证据调整任务内策略及尚未执行的计划。必须区分固定承诺与可改执行方法，不能把所有语义选择预编译为规则，也不能让一次自然语言修正覆盖历史事实。

B3. ACP 应成为标准 Agent 连接与会话通道，但替换委派入口不自动提供隔离、授权、恢复、独立 Review 或质量保证。现有 Ultra runner 已有 ACP driver；需要比较它与 `agent-delegation`／ACPX 的职责，决定复用、收敛和删除边界，而非叠加两套控制器。

B4. 正常自动化需要闭合：接受边界 → 计划当前有限工作 → 启动独立执行 → 非模型等待 → 观察真实结果 → 验证与 Review → 接受、修复、重规划或停止 → 汇总交付。退出码、进程退出和 ACP terminal 都不能单独裁决产品完成。

B5. 循环反馈至少分两层：任务内根据执行证据修复代码、改变策略和重规划；跨任务根据保留样本产生图／Prompt／Skill／路由候选，比较独立样本后晋升。第二层需要评测与回滚；两层都不能偷偷改 Owner 的验收和权限。

B6. 首先比较现有原生 Host 能力、现有 Ultra runner 与 ACPX；新增机械运行组件必须说明它解决的现有缺口。独立 CLI 与未来 PaaS 是部署和产品入口方向，不等于现在引入新的语义数据库或全局常驻调度器。

## 第一轮外部证据与立场限制

完整检索来源、适用范围和反证见 [Codex 证据目录](./evidence-codex.zh-CN.md)。截至冻结时，已实际联网检索并读取下列正文或论文内文。

- C1（OpenAI 工程经验）支持 A3/A4/B5：将意图与反馈写入可发现的仓库材料，按需读取；机制应保留局部 Agent 自主性。案例不能证明 UBP 的当前体验。
- C2（Anthropic 长时应用工程）支持 A2/B4，同时挑战“越多循环越好”：真实交互 QA 找到核心假功能；同一团队后来移除不再必要的 sprint／reset。应逐个消融，不凭感觉全删或全保留。
- C3（Google ADK 2.0 官方机制）支持 B2：静态图、动态代码流程、循环构件并存。图与 loop 是不同视角，不能分别绑定新项目和老项目。这里借鉴机制，不提议引入 ADK 依赖。
- C4（ACP v1 规范）支持 B3/B4：prompt turn、更新、权限请求、取消与停止原因是连接机制；`end_turn` 不是软件验收。不能将 v2 文档或未来能力误写为本地 transport 已具备。
- C5（AFlow）支持 B5 的图候选搜索：以执行评估反馈优化代码表示的工作流，并在验证集重复运行。其有明确评分的 benchmark 不等于开放软件项目全自动演化已经成立。
- C6（GEPA）支持 B5 的 Prompt 改进：利用执行／评估轨迹产生候选、比较和选择，核心是 Prompt 优化；它不能单独证明图调度、权限和持久运行已解决。
- C7（Google DeepMind 等的自纠错研究）挑战“多问几次自然会变好”：无外部反馈的自纠错和对抗可能退步，比较时需相当推理预算。该研究的旧模型结果不构成 2026 年模型能力上限。

第一轮请 Claude Code 优先攻击：我们的 Owner 体验修改是否只是换了一套卡片；过度保护验收是否压制任务内探索；现有 ACP Skill 能否承接真实工厂生命周期；如何让图自动改进而不把 optimizer 变成新的流程负担；多模型 Review 在哪些条件下值得其成本。
